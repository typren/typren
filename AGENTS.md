# Agent guide

Instructions for AI coding agents working in this repository, whatever tool is
driving them. The binding contract is [CONTRIBUTING.md](CONTRIBUTING.md); this
file is the agent-oriented distillation plus the mistakes agents make most.
Follow both. When they disagree, CONTRIBUTING.md wins.

## Ground rules

- Read [CONTRIBUTING.md](CONTRIBUTING.md) before writing code. The CLA section
  is a real constraint on whether your human's work can be merged at all.
- The gate is local: `bun install`, then `bun run verify` must pass before you
  claim anything is done. There is no server-side test CI to catch you; the
  pre-push hook is the gate, and `--no-verify` is never the answer.
- Pull requests target `develop`, never `main`.
- Conventional Commits, one concern per commit. The body explains **why**; the
  diff already says what.
- Any change to a published package needs a changeset (`bun changeset`).
  Pre-1.0, breaking changes bump **minor**.
- New code needs 90% line coverage against the merge-base. Tests are colocated:
  `foo.ts` gets `foo.test.ts`.

## Architecture rules — where agents go wrong most

Read the Architecture section of the [README](README.md#architecture) first.
Four layers, each depending only on the one below:
`ContentAdapter` → `ContentStore` → `makeActions()` → editor UI. Work out which
single layer a change belongs to before writing it. Most features are a method
on an existing interface, not a new abstraction.

- **Adapters are interfaces plus `create*Adapter(opts)` factory functions.**
  Never classes, never a DI container.
- **Trust boundaries belong to the adapter.** Slug, locale and media-id
  validation happens inside the adapter, not in callers. Never assume an
  upstream layer checked.
- **Fail closed.** Every `AuthAdapter.authorize()` wraps identity resolution in
  try/catch and returns `false` on error. A thrown error must never default to
  allowed.
- **Theming is the `--typren-*` CSS variable set, and nothing else.** New
  visual tokens join that set with a shadcn-token fallback. No component-local
  variables, no hardcoded colors.
- **`ponytail:` comments are intentional.** They mark a deliberate shortcut
  with its ceiling and upgrade path. Read the ones near code you change; do
  not "fix" them into abstractions, and do not delete them while their
  shortcut stands.

## Style

- Smallest working diff. Reuse what the codebase already has before writing
  new code; check the standard library and existing dependencies before
  proposing a new dependency. A new dependency needs its justification in the
  commit body.
- No speculative abstractions: no interface with one implementation, no config
  for a value that never changes, no scaffolding for imagined futures.
- Comments state a constraint or a why the code cannot express. Never narrate
  what the next line does, and never leave comments that talk to your reviewer
  ("added this to fix…").
- Match the surrounding code's naming, idiom and comment density. Complete
  sentences in comments and docs.

## Attribution

Commits are authored by the human contributor who reviewed the work and signs
the CLA. Do not add tool-attribution trailers or "generated by" lines; the
contribution's legal author is the human, and the CLA check keys off commit
authorship.
